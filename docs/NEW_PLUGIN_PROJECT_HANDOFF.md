# Milky Way Idle 新插件项目启动交接文档

> 使用方法：新建插件项目后，可以在第一次对话中把本文件完整发给 Agent，作为项目背景和工程约束。本文描述的是可复用的工程经验，不代表新插件的具体功能需求；正式开工前仍需补充插件名称、核心功能、数据来源、界面入口和发布方式。

## 给新项目 Agent 的首轮指令

这是一个新的 Milky Way Idle Tampermonkey 插件项目。请先阅读并遵守本文，不要直接复制旧插件的业务代码、生成物、版本历史或发布配置。

在开始改动前，请先完成以下工作：

1. 阅读当前项目目录、`AGENTS.md`、`README.md`、`package.json` 和已有源码，不要凭空假设工程状态。
2. 用简短文字复述你理解的新插件目标、产品边界、数据来源和主要风险。
3. 判断用户提出的实现方式是否合理；若有更简单、安全、稳定或自动化的方案，说明理由并优先采用更好的方案。
4. 说明准备修改的文件或模块、修改理由、风险或不确定点，以及验证方法。
5. 只有会显著影响结果的关键信息缺失时才提问；可以安全推断的小细节不要反复确认。
6. 默认做最小必要修改，保持模块边界，不做无关重构。
7. 未经明确授权，不提交、推送、发布、删除用户数据或扩大插件权限。

## 背景与总体判断

已有参考项目“银河奶牛信用点助手”是一款 Milky Way Idle 只读规划型 userscript。它已经沉淀了较完整的源码管理、数据适配、持久化、测试、构建和发布机制。

新插件应复用这些工程方法，而不是把第二个独立产品直接嵌套在旧项目仓库中。默认推荐把新插件建立为同级独立目录和独立 Git 仓库：

```text
01_软件与插件项目/
├── 银河奶牛信用点助手/       # 旧参考项目
├── 银河奶牛-新插件名/         # 新插件独立项目
└── 银河奶牛共享参考资料/      # 可选，只读共享参考
```

旧仓库的构建入口、版本号、产物名称、发布白名单、GitHub 地址和 Greasy Fork 地址都按单一插件设计。在旧仓库中嵌套第二个插件，会让格式检查、构建产物、版本管理和发布范围互相干扰。只有两个插件确实需要共享代码、统一版本和同时发布时，才考虑改造成 monorepo。

## 产品与安全边界

在新功能尚未明确前，采用最小权限和只读优先原则：

- 不自动购买、出售、兑换、升级或提交其他游戏操作。
- 不读取登录凭据、令牌或与功能无关的账号信息。
- 不上传角色或账号数据，除非用户明确要求、定义上传字段、目的、接收方、保留策略和用户授权流程。
- 优先读取游戏页面已经公开或已经接收的数据，不主动制造额外游戏操作。
- Userscript 的 `@grant`、`@connect` 和匹配域名只声明实际需要的最小集合；避免 `@connect *`。
- 估算结果必须明确标注数据来源、时效和局限，不能把市场快照或单档报价描述成完整成交保证。

如果新插件需要同步、上传或自动化操作，Agent 必须先把它识别为新的产品边界，单独说明隐私、安全、服务端和误操作风险，不能从旧项目的只读边界中默默扩展权限。

## 文件和模块职责

### 源码与产物

- `src/` 是人工维护源码的单一事实来源。
- `dist/` 只保存当前可安装脚本、开发加载器、开发运行时和测试台等生成物。
- `releases/vMAJOR.MINOR/` 保存不可变的历史正式版本。
- `references/` 保存第三方参考实现，不得成为默认构建输入。
- `.workbench/` 保存截图、补丁、探索代码和未完成预览，并由 Git 忽略。
- 不要手工编辑 `dist/` 或 `releases/`；必须通过构建或发布脚本生成。

### 业务与运行时

- `src/core.js`：纯计算、排序、筛选和可复用业务规则。
- `src/runtime/config.js`：稳定常量、URL、存储键、功能开关和数据版本。
- `src/runtime/storage.js`：本地状态校验、迁移和持久化。
- `src/runtime/game-state.js`：游戏字段别名、数据形状和局部/完整快照语义归一化。
- `src/runtime/game-data.js`：初始化数据、缓存和较新实时数据的协调。
- `src/runtime/scheduler.js`：防抖、按帧合并、高频刷新协调和生命周期取消。
- `src/bridge.js`：被动读取游戏消息或页面 API；避免承担业务计算和 UI 渲染。
- `src/ui/`：按功能拆分渲染、交互和样式。
- `src/localization.js`：所有用户可见的中英文文案。
- `src/userscript.js`：组合根，只负责依赖组装、入口挂载、共享状态和统一销毁。

新增业务规则时，优先写纯函数和测试，再接入运行时和 UI。不要让业务计算直接依赖网页 DOM，也不要让 `userscript.js` 继续膨胀成所有功能的集合。

## 游戏数据处理经验

### 使用稳定标识

- 内部状态优先使用 HRID 等稳定标识，不使用翻译后的名称作为主键。
- 中文名称优先来自游戏官方 i18n；暂时不可用时可以使用有版本的本地缓存，仍未命中时诚实回退原始名称。
- UI 识别确实需要文本兜底时，应集中维护中英文别名，不能把散落的中文选择器当成主数据协议。

### 区分数据语义

以下情况不能混为一谈：

- 字段没有出现；
- 字段明确为空；
- 局部增量消息没有包含某项；
- 完整初始化快照省略某项，且游戏语义规定省略等于默认值；
- 数据正在加载；
- 数据加载完成但结果为空；
- 数据读取失败。

错误地合并这些状态，容易造成插件虚构库存、等级、余额或市场结果。

### 协调多个来源

如果同一信息来自公开快照、页面缓存、实时消息和 DOM 兜底，应先定义清晰的优先级和一致性规则：

- 验证每种数据源的结构和时间戳。
- 买价和卖价等独立字段分别更新，不因单边缺失清空另一边。
- 新实时数据通常优先于旧静态快照。
- 不完整快照不能立即覆盖更完整的数据。
- 并发读取合并为一次请求。
- 添加合理的缓存有效期、刷新冷却、超时和失败退避。
- DOM 只作为窄范围兜底，并且只读取玩家已经打开或页面已经展示的内容。

若已有 bridge 和数据协调模块覆盖某种消息，不要再安装第二条竞争性的 WebSocket 拦截和状态仲裁路径。

## 本地存储经验

不要在各功能中散落未经验证的 `localStorage` 或 GM 存储调用。建议：

- 所有存储键集中定义，并使用新插件独有前缀。
- 读取时验证对象结构、枚举、字符串格式、数字范围和数组成员。
- 损坏或旧版本数据安全回退，不能让插件启动失败。
- 明确定义向后兼容迁移。
- 区分“用户明确清空”和“从未设置”。
- 需要时按站点、角色或账号可见标识隔离状态。
- 写入函数返回成功或失败，敏感交互不能假设持久化一定成功。

两个插件同时安装时，下列标识必须各自唯一：

- DOM id 和 CSS class 前缀；
- 全局变量和桥接对象名；
- localStorage、sessionStorage 和 GM 存储键；
- 自定义事件名；
- 开发运行时标记；
- 控制台日志前缀。

## UI 与可访问性经验

- UI 按功能拆入 `src/ui/`，不要把所有 HTML、事件和样式堆在入口文件。
- 中文和英文都应走统一的本地化入口，避免运行时界面残留写死文案。
- 游戏语言在启动阶段可能短暂不一致，应优先参考当前可见界面，并允许之后更新语言而不丢失页面、设置、焦点和计划状态。
- 渲染前后保留用户焦点和当前操作对象，避免整个区域重绘后焦点丢失。
- 标签页、弹窗、折叠区、状态提示和拖动排序应包含相应的 ARIA 状态及键盘路径。
- 不要遮挡游戏原生拖动区、弹窗和可点击目标。
- 对复杂界面建立测试台，在多个宽度和中英文环境检查横向溢出、控件重叠、焦点、键盘操作和状态持久化。

只凭单张截图判断响应式布局不够可靠；测试台应输出可由自动化读取的检查结果和完成状态。

## 构建与开发方式

推荐延续旧项目的确定性构建方法：

- 构建脚本维护显式 `SOURCE_FILES`，按依赖顺序拼接源码。
- `src/userscript.js` 必须最后执行。
- 生成运行时保留源码边界注释，方便浏览器调试。
- 正式 userscript 尽量不依赖本机开发服务和 npm 运行时包。
- 提供本地开发服务和 Tampermonkey 开发加载器。
- 开发加载器使用独有 runtime 标记并避免浏览器缓存。
- 新增运行时文件时同步更新构建清单和模块顺序测试。

如果新插件需要 TypeScript、npm 运行时依赖、代码分割或复杂资源处理，再评估 esbuild 等构建器；不要仅为追求形式增加构建复杂度。

## 测试与质量门禁

建议保留以下基础命令：

```bash
npm ci
npm test
npm run format:check
npm run lint
npm run build
npm run verify:repo
npm run check
npm run check:ci
```

`npm run check` 应覆盖：

```text
格式检查 → 静态检查 → Node 测试 → 确定性构建 → 仓库结构校验
```

`check:ci` 应在构建后检查 Git 差异，防止源码已变更但提交的生成物仍然过期。

测试优先覆盖：

- 纯计算正确性和边界条件；
- 数据字段别名与局部/完整快照；
- 损坏存储和旧版本迁移；
- 缓存时效、并发合并、超时和退避；
- 调度器的合并与销毁；
- WebSocket 或页面桥接只处理预期域名和消息；
- 中英文文案与数字格式；
- DOM 转义、事件语义和原生控件兼容；
- 构建模块顺序、仓库结构和发布白名单；
- 历史发布不可覆盖。

## 发布管理经验

正式发布流程应包含以下护栏：

1. 支持完全只读的 `release:dry-run`。
2. 检查当前分支、远端仓库、上游同步状态和空暂存区。
3. 使用 `X.Y.Z` 语义版本，并明确版本递增规则。
4. 更新 CHANGELOG 后运行完整检查。
5. 普通构建只更新 `dist/`；正式发布才新增历史归档。
6. 历史归档采用 append-only 策略，同一版本字节不同必须报错，不能覆盖。
7. 发布清单记录版本、相对路径、文件大小和 SHA-256。
8. 只显式暂存发布白名单文件，禁止 `git add .`。
9. 提交和推送必须经过用户明确授权。
10. 推送后核对远端提交和公开分发平台版本。

错误版本的回滚方式是修复源码并发布更高补丁版本，不重写已经发布的历史文件。

## 第三方参考插件及使用边界

第三方参考只能用于理解游戏数据、交互和设计思路。复制代码前必须检查来源、版本、许可证、依赖和安全行为。

### MWI Guild Donation Value 0.7.6

- 许可证：MIT。
- 可参考：市场和公会规划思路、游戏 i18n、设置持久化、浮动面板。
- 限制：如果新项目已有自己的 bridge 和市场缓存，不要从该插件再引入第二套 WebSocket 和市场状态仲裁。

### MWITools

- 许可证：CC-BY-NC-SA-4.0。
- 特点：大型综合插件，包含大量页面适配、React/DOM 定位、快捷键、拖动、弹窗、市场和数据工具经验。
- 限制：代码量大、权限和外部依赖多；其 ShareAlike 与非商业限制不能默认兼容新项目的 MIT 发布。适合观察行为和数据形状，不应作为直接复制的代码底座。

### MWIEnhancementCalculator

- 特点：从大型插件中提炼纯计算模块，展示了输入归一化、Node/浏览器双环境和数学模型测试化的良好思路。
- 限制：它声明源自 MWITools，独立文件没有消除上游许可证约束。复用代码前必须确认授权、署名及许可证兼容性。

### 学学中秋月饼

- 许可证：文件头声明 MIT。
- 可参考：强化成本、市场交互和双语界面。
- 限制：依赖 MWITools 市场数据以及 mathjs、lz-string、pako。不要未经评估就让新插件形成对另一个 userscript 的运行时依赖。

### MWI 试炼同步

- 许可证：MIT。
- 可参考：名称缓存、中英文界面、卡片高亮和 GM 存储。
- 限制：包含角色数据上传、外部服务器连接、定时轮询和宽泛网络权限，不符合只读且不上传数据的默认安全边界。

### 参考资料管理规范

- 记录原始文件名、上游地址、版本、许可证、用途和 SHA-256。
- 本地参考插件可以 Git 忽略，但应保留一份可审计的哈希清单。
- `references/` 永远不是构建输入。
- 不要机械格式化或重写第三方参考文件。
- 复制实现前检查行为、出处、许可证和是否包含外部网络或账号数据逻辑。
- 即使许可证允许复制，也优先重新实现必要的最小逻辑，并保留适当署名。

## 从旧项目迁移时必须重新配置的内容

以下内容不能原样复制：

- `package.json` 的名称、描述和版本；
- Userscript 的名称、namespace、描述、匹配域名、权限和更新地址；
- 构建产物、开发加载器和历史归档文件名；
- `SOURCE_FILES` 及其依赖顺序；
- DOM、CSS、存储键、事件名、全局对象和日志前缀；
- GitHub 仓库地址、目标分支和远端校验规则；
- Greasy Fork 或其他分发平台地址；
- 发布白名单和仓库校验正则；
- README、CHANGELOG、架构文档及产品安全边界；
- 旧插件业务数据、业务模块和业务测试；
- `dist/`、`releases/`、旧版本号和旧发布历史。

可以优先移植但仍需重命名和审查的内容：

- `.editorconfig`、`.gitattributes`、Prettier 和 ESLint 配置；
- Node 测试框架和 CI 基础流程；
- 确定性构建脚本结构；
- 开发服务器与开发加载器模式；
- 仓库结构校验思路；
- 发布 dry-run、白名单暂存和不可变归档机制；
- 通用 DOM 转义、调度器和存储验证模式；
- 架构、开发和发布文档模板。

## 新项目开工前需要确认的信息

Agent 应先从用户描述和现有文件中寻找答案，无法确定且会影响架构时再询问：

1. 新插件解决什么具体问题，用户完成任务的完整流程是什么？
2. 插件是纯展示/规划、被动辅助、数据同步，还是会执行游戏操作？
3. 需要读取哪些游戏数据，来源是初始化消息、实时消息、页面 API、DOM、公开快照还是外部接口？
4. UI 放在游戏侧栏、原生弹窗旁、独立浮窗，还是只提供后台能力？
5. 是否需要中文和英文、移动端和窄侧栏支持？
6. 哪些状态需要持久化，是否按站点和角色隔离？
7. 是否需要与其他插件共存或读取其他插件的数据？
8. 最终通过何种渠道安装和更新，是否需要 GitHub、Greasy Fork及备用分发源？
9. 新插件采用什么许可证，第三方参考代码是否与其兼容？

## 建议的实施顺序

1. 定义产品边界、可观察行为和不做什么。
2. 列出数据来源、数据契约、失败状态和权限需求。
3. 建立独立仓库及最小工程脚手架。
4. 先实现纯业务规则及测试。
5. 增加游戏状态适配、存储和调度模块。
6. 接入只读 bridge 或页面数据源。
7. 构建最小 UI，再补双语、键盘、焦点和响应式行为。
8. 建立开发加载器和浏览器测试台。
9. 完成仓库校验、构建和 CI。
10. 在用户明确授权后配置并执行正式发布。

## 首轮输出期望

收到本文和新插件功能说明后，Agent 的第一次回复应包含：

- 对插件目标和用户流程的简短理解；
- 推荐的产品边界与最小权限；
